## Database/API preparation: use the existing implementation

| Requested concept | Current representation | Rule to preserve |
| --- | --- | --- |
| Products | `products` | Server/database controls price, metadata and publication |
| Orders | `orders` | Immutable product/price snapshot; constrained transitions and versions |
| Payment Claims | Claim fields on `orders`, created from `ai_checkout_sessions` | Canonical unique TrxID; one accepted claim per session; identical retries return the same order |
| Admin Users | `admin_users`, provider identity, `ai_admin_sessions` | Active allowlist and enrolled MFA; verify each API operation |
| Audit Logs | `audit_logs`, with internal notes in `ai_order_notes` | Status/note/audit changes commit together; private, append-only runtime audit access |

A separate Payment Claims table is not added just to match a name in a brief.
The existing one-claim-per-order model already implements that responsibility.
Multiple corrected claims would require an agreed business rule and an additive
migration, preserving historical TrxID uniqueness. Original Phase 2 `pending`
rows remain; new web quotes live separately until a submitted claim exists.

The normal web flow remains `submitted → verified → delivered`, or
`submitted → rejected`. Refunds require an approved procedure. Original tables,
encrypted voucher structures and terminal utilities are retained without enabling
voucher sales. See `architecture-continuation.md`, `database.md` and `api.md`.
